# 互联网接入验证

维护日期：2026-10-29。范围为用户已确认的第一阶段技术验证，尚未接入正式客户端、中央管理 App 或安装包，没有发布或改动正式中央。临时公网验证服务与正式部署分开记录。

## 已确认的目标

- 自己和受邀同事跨网络使用；普通用户只安装远舟，通过配对接入。
- 中央与客户端优先直连，无法直连时由公网中继转发；发现/协调服务承担少量控制流量。
- 端到端加密；中央继续推理和编排，客户端系统操作仍统一经 Local Agent 执行。
- 不新增文件大小、传输总量、速率、任务时长、对话数、设备数或中继流量额度；直连和中继的业务能力一致。保留现有身份、撤销、审批和文件完整性校验。
- 连接建立期限、故障探测、流控和有界工作缓冲区不作为业务额度，不能据此截断文件或自动重放未知结果的任务。

## 候选与集成边界

首选验证对象为 `iroh = 1.4.1`（MIT / Apache-2.0，最低 Rust 1.91），采用加密 QUIC 流、端点公钥身份、直连路径探测和自建 HTTPS 中继。固定版本与传递依赖保存在根 `Cargo.lock`，没有使用滚动 `latest`。

选它的原因是现有两个原生 App 与 Agent 都使用 Rust/Tokio，且流式字节接口可以适配现有 WSS/HTTPS，无须新增系统虚拟网卡或让用户另装组网 App。WebRTC/ICE + TURN 是备选，但还需独立设计信令、DataChannel 字节流适配与原生生命周期；本轮没有同时引入第二套栈。

上游通常先经中继完成连接握手，再尝试直连。本轮 `connect_prefer_direct` 在返回连接、允许应用打开流前等待直连窗口；到期且中继可用时使用中继，不重发业务。该等待只是连接策略，不限制连接后的任务时长。1.4.1 的默认路径选择器把 IP 路径列为 primary、relay 列为 backup；不需要使用不稳定自定义传输 API。

探针使用 `presets::Minimal`，没有隐式启用第三方公共发现/中继，没有开启自动路由器端口映射。临时中继仅绑定本机回环，使用显式信任的临时证书，没有关闭 TLS 验证。测试中继允许探针端点接入，**不能直接把这个测试配置部署为公开中继**；远端部署时须接入受邀设备认证，不能成为匿名流量出口。

`PeerStream` 仅实现 `AsyncRead/AsyncWrite` 字节适配，不解析、路由或执行设备命令。测试 WSS 服务只回显合成消息，不是产品网关或 Fake Central 替代入口。

## 本机复现

在仓库根目录执行，避免与其他 Cargo 构建争用锁：

```powershell
cargo test -p peer-transport --locked -- --test-threads=1
cargo build -p peer-transport --example peer-probe --locked
node tests/smoke/peer-transport-probe-smoke.mjs
```

七项传输测试覆盖：

1. 无中继直连、流式 SHA-256 往返、重复开流及显式新建连接。
2. 直连和中继都可用时选中直连；从中继计数器核对大块业务未走中继，关闭中继后已有直连继续传输。
3. 发现地址中的身份不能替换受信身份。
4. 已加密但未受邀请的端点被拒绝，连接关闭且不能打开业务流。
5. 禁用 IP 传输模拟直连不可用，中继实际转发往返数据，以计数器证明不是仅显示中继标签。
6. 使用与端点相同的 CA 配置，针对真实临时中继 TLS 服务观察 `UnknownIssuer`，并核对不受信端点无法上线。没有把等待超时单独当作证书拒绝证据。
7. 中继 QUIC 流中承载真实 WSS，正确主机名成功，错误主机名以 `NotValidForName` 失败。

流式样本为 8 MiB + 17 字节，工作缓冲区 64 KiB；这两者都不是业务总量上限。测试期限只用于让失效测试及时结束。结果写入 `target/peer-transport/`，不提交原始地址、证书或秘密。

## 打洞失败的实现与时序排查

2026-10-29 用户要求先检查探针实现和连接时序。本轮仅检查固定依赖 iroh / iroh-relay 1.4.1 源码并运行 Windows 本机回环测试，没有连接或重新部署 ECS / Mac，没有修改正式服务、系统防火墙或产品代码。

已确认的实现行为：

- `Endpoint::online()` 只等待至少一个中继完成注册握手，不保证 QUIC 地址发现（QAD）已经获得公网 UDP 候选地址。当前探针把这一时刻作为输出地址、开始配对的前提，没有独立记录 UDP 就绪状态。
- `RelayMode::custom([url])` 使用默认 QAD UDP 7842；它不会把 HTTPS 38443 当作 QAD 端口。固定版本默认启用 QUIC 多路径和 NAT 候选交换，`Minimal` 预设本身没有关闭这些能力。静态检查未发现这些开关或端口配错，但不代表现场 UDP 已经可达。
- WAN 驱动只输入对端身份和中继地址，依赖库交换直连候选。这一方式在本机真实 TLS / QUIC 对照中可行：新增 `relay_only_address_bootstrap_can_reach_direct` 回归，初始地址不含 IP，直连等待设为零，实际先返回 Relay，再于连接尝试开始后约 33 毫秒选中 Direct；8 MiB + 17 字节双向回显和 SHA-256 通过，传输窗口中继发送增量仅 8,914 字节控制流量。该时间为一次本机观测，不是性能保证，也不证明 WAN NAT 可穿透。本地中继未启用 QAD，此用例验证候选交换和后续直连，不验证公网地址发现。
- `connect_prefer_direct` 的 3 秒等待到期只返回已有连接，不会禁用 UDP 或后续直连升级。固定版本对候选未变化的再次打洞触发有 5 秒间隔处理，并有 60 秒连接升级检查；不能解读成无条件每 5 秒重试或首次连接必须等 60 秒。

上次 WAN 探针的观测缺口：

- 自动兜底用例在连接建立后等待约 3 秒，传输约 1.644 秒后立即关闭。约 4.6 秒的握手后观察窗口可能遗漏后续路径升级；这只能证明观察不足，尚不能认定延长等待即可修复直连。
- 只记录传输前后两个选中路径快照，没有连续路径事件；原生探针没有初始化底层 tracing 订阅，驱动又丢弃 stderr。历史记录无法还原 QAD 成败、候选变化、打洞轮次或失败原因。
- 每个用例重启探针，未验证同一连接长期保持中继后升级直连。驱动的 `ready` 表示已写入配对输入，并不严格证明原生监听已进入 accept；首轮过期监听的尝试此前已剔除，不能混入两轮有效传输结果。

结论仍为**跨网中继通过，直连根因未确定**。目前排除了“等待结束就永久中继”和“只给中继地址必然无法直连”两种实现层面的推断；公网 UDP 探测失败、候选不足、NAT 映射/过滤和观察窗口过短仍需新证据区分，不能归因于某运营商或防火墙。

下一步方案（尚未实施）：仅增强隔离探针，记录单调时钟下的中继就绪、QAD / 候选变化、建连、打洞与路径事件；原始网络地址日志私有保存，提交报告只含脱敏分类、数量与耗时。把开始使用中继的等待与连接持续观察分开，在同一连接上继续小流量探测并观察至少 90 秒，避免传完即关闭；同步调整监听退出时序和驱动完成判定，分别报告传输成功与直连是否建立。先本机验证，再安排新的临时跨网测试，不复用已清理的部署。上述时间和样本是测试安排，不新增产品限时、限速、流量或文件额度。

## 双机探针运行方式

在已授权的隔离环境准备自建中继后，两台机器使用相同源码构建 `peer-probe`。设置 `PEER_PROBE_RELAY_URL` 为实际 HTTPS 中继；私有测试 CA 可通过 `PEER_PROBE_CA_FILE` 指定，不导入系统信任、不跳过主机名校验。

一侧运行 `peer-probe listen`，另一侧运行 `peer-probe dial`。双方第一行只包含公开 `EndpointAddr`，经受信运维通道互换并输入对方进程 stdin。它含网络地址，应留在私有验收材料，不提交到公开仓库。该交换模拟可信配对材料，**尚未实现公网发现服务和产品配对流程**。

探针仅允许匹配的端点公钥接入，发送生成数据，校验长度和 SHA-256，正常结束关闭连接；不读取业务文件，不调用模型或执行命令。`PEER_PROBE_BYTES` 可改变样本大小，不设业务总量额度。`PEER_PROBE_RELAY_ONLY=1` 是测试故障注入开关，用于强制验证中继，不是产品功能开关。

默认探针身份仅驻留内存。公网验证可用 `PEER_PROBE_SECRET_FILE` 读取独立生成的 32 字节私钥种子，提前把对应公钥登记到中继准入名单；种子保存在权限受限的私有验证目录，不经 URL、命令参数或日志传递，不复用正式设备身份。`PEER_PROBE_ACCEPT_SECS` 只调整监听探针等待对端的测试期限，便于操作者切换热点，不截断已经建立的数据流。

跨网驱动运行方式为 `node tests/smoke/peer-transport-wan-probe.mjs <私有配置.json> listen|dial`。配置指定 `executable`、`secretFile`、`caFile`、`identity`、`peerIdentity`、`relayUrl`、`reportFile`、`scope` 和 `cases`；可选 `sampleBytes`、`acceptSeconds`、`interCaseDelayMs`。每个用例包含 `name`、`relayOnly` 和可选 `expectedRoute`。两侧按相同顺序运行，初始仅交换受信公钥和中继地址，不预填 IP 直连候选；由 iroh 发现路径。驱动不记录地址和密钥，校验实际进程公钥与登记身份相符；未知失败不自动重放。用例之间的等待仅用于采集中继计数器，不限制连接内的速率。

远端启用前仍需复核端口占用和资源状态，验证旧系统兼容性、专用 HTTPS 证书、受邀端点认证、实际网络和临时资源清理方式。使用成熟 relay 服务的部署配置，不把本机 AllowAll 夹具原样暴露到互联网。公网中继的业务转发量取决于真实直连成功率，当前没有给出成功率、费用或容量承诺。

## 验证边界与下一步

本机 socket 成功不代表已经完成 NAT 打洞或跨运营商验收；禁用直连传输的静态兜底测试也不等于传输中断网切换测试。

仍需验证：

- Windows 客户端与 Mac 中央的真实跨网路径、家庭宽带/热点/受限网络、IPv4/IPv6。
- 中途直连失效转中继、网络恢复后回到直连、完全断网及中继重启；核对路径事件和传输完整性。
- 中继只处理密文的部署核查与抓包证据，以及发现信息篡改、重放、设备撤销与密钥轮换。
- 真正中央网关、双 WSS、Local Agent、HTTP 更新下载、模型任务与客户端文件/命令链路。合成回显不代替这些验收。
- 产品配对与既有设备身份迁移、中央和客户端连接组件生命周期、连接状态 UI。
- Mac 构建与旧 Windows 兼容性。不能因为库能在本机 Windows 编译，就承诺所有现有客户端系统均受支持。

下一步是在用户提供的公网环境完成临时中继和两端原生探针验收，再据结果确认第二阶段产品集成；未经新的明确范围确认不切换正式服务或发布安装包。
