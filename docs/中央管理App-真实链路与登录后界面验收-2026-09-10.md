## 2. 真实链路的组织方式

原生测试先建立新的隔离运行目录，生成只供本次测试的 CA 与覆盖 `central-test.invalid`、`localhost`、`127.0.0.1` 的服务器证书。保存配置使用合法的合成客户端域名；测试传输连接本机随机端口，正常校验 TLS，无 hosts 修改。它读取编译内置的完整候选清单并启动原生 `Service`，以随机管理员密码登录 `People`，创建配对专用用户并生成一次性配对码。

真实模型账号只由原生测试通过 `model_accounts::import_existing` 导入该次临时 DPAPI 库，然后通过现有服务内存 bootstrap 接入网关。Node 客户端、Local Agent 和 UI socket helper 不读取本机 Codex 登录源，也不接收上游模型凭据。现有登录源不修改；测试不执行账号刷新或把原始登录写入公开证据目录。

原生为 Node 测试进程建立独立 `KILL_ON_JOB_CLOSE` Job。Node 被分配进 Job 后，原生才写入完整首行 bootstrap；Node 在读完并校验首行之前不得启动任何子进程。原生总工作窗口为 270 秒，整体超过 300 秒不能记为通过，超时进入清理。

Node 调用新 Rust example 完成设备配对和真实 `/ws` 连接。example 复用 `device_token::pair` 和 `device_token::agent_socket`；后者可以连接 UI 的 `/ws`，并保留既有 TLS 与 Bearer 验证。设备令牌留在原生私密存储内，不导出给 Node；helper 只输出配对 deviceId 和网关消息。

Node 随后启动实际 `local-agent.exe`，使用临时 token store 和临时工作区。Local Agent 通过 `/ws/agent` 主动出站连接同一网关。目标和配对参数由父进程 stdin 传入，不以配对码、令牌或管理员密码作为命令行参数。Local Agent 本身沿用既有产品参数传递非秘密的工作区、网关地址及设备 ID。

### 一次 Turn 的证据

测试只在新临时客户端工作区预置 `input.txt` 和 `proof.ps1`。`input.txt` 含随机标记；`proof.ps1` 的命令回执标记在真实执行时才生成，并写入 `proof.txt`。

客户端先通过真实 AgentRPC 校验工作区读取，再创建一个 Thread、发起一个模型 Turn，明确要求模型：读取 `input.txt`；通过 `device_exec` 执行固定 PowerShell 测试脚本一次；读取 `proof.txt`；在回答中复述两个原始随机标记。Node 不自行执行该脚本，也不把随机标记放入模型提示词。

通过证据必须同时包含：

1. 初始化返回受信 marker `yuan-zhou-remote-workspace/1`。
2. 实际 Local Agent 的直接文件读取成功，原生用户设备清单观察到该设备在线。
3. 模型的真实 `device.tool.*` 事件至少有两次成功读取、恰好一次成功命令，命令退出码为 0。
4. Turn 成功完成，回答包含客户端文件和命令新生成的两个随机标记，预置脚本未被改写。
5. 原生 `People` 撤销设备后，UI socket 得到 `4001/DEVICE_REVOKED`，Local Agent 输出固定撤销终态并自然退出，本地令牌被移除。
6. Node 及其子进程退出、受管服务和 Job 清理均有证据。

### 命令边界说明

当前网关 `device_exec` 直接分发给 Local Agent；现有 `pendingDeviceApprovals` 用于工作区 patch，不是命令通用审批。这个测试因此是**事后证据核验，不是执行前命令白名单或命令沙箱**。

脚本给模型明确限定测试程序、参数和相对工作目录，并核对实际工具事件、退出码、回执文件与模型回答。观察到非预期工具或命令时立即请求中断并判失败。所有中央系统审批、文件 patch 审批和未知审批都拒绝。由于网关当前事件不提供完整 exec 参数，这不能证明执行前对所有参数进行了强制 allowlist 检查。测试仅请求新建临时工作区，不请求业务文件或其他目录。

## 3. stdin/stdout 契约

`central-live-client-qa.mjs` 不使用业务命令行参数，由原生一次性写入 JSON 行：

```text
{gateway,caPath,code,agentBinary,helperBinary,workspace,output,model}
```

其中 `gateway` 为本次随机端口的本机 `wss://.../ws`；`helperBinary` 是新 `central-live-client.exe`，不是旧 `platform-acceptance.exe`；`output` 是公开 `client-result.json` 文件路径。模型固定为 `gpt-6-astra`。工作区和令牌库位于同一个本次临时根下，公开输出在临时私密根之外。不要手工把含配对码的 JSON 放进终端命令、日志或版本库。

父进程保持 stdin 打开。EOF 表示取消，不表示 bootstrap 输入完成。输出为有界 NDJSON，仅包含公开阶段：

```text
{phase:"paired",deviceId}
{phase:"completed",deviceId,evidence,summary}
{phase:"revoked",deviceId,agentExited:true}
```

`completed.evidence` 必须同时具有以下七项 `true`：`actualLocalAgent`、`workspaceReadVerified`、`modelToolReadVerified`、`modelToolExecVerified`、`randomProofVerified`、`turnCompleted`、`runtimeMarkerVerified`。

`summary` 只包括两个标记的 SHA256、读取/命令计数和固定 marker。原生在 `completed` 后通过 `People` 撤销设备，等待 `revoked`、stdio 排空和子进程成功退出。单独的 `completed` 不能算整条测试通过。失败输出只允许 `{phase:"failed",code:"QA_..."}`；不输出原始错误、模型回答、令牌或 bootstrap。

## 4. 真实链路运行方法

以下为复现命令，本轮执行结果见第 7 节。应在用户已授权真实模型调用的会话中执行。先确认没有其它 Cargo/Tauri 构建占用锁。工作目录为 `C:/Workplace/central-codex-platform/spikes/local-dev`。涉及 DPAPI、ACL 的验收使用实际 Windows 用户上下文。

先构建真实客户端组件：

```powershell
cargo build -p platform-security --example central-live-client
cargo build -p local-agent
node --check scripts/central-live-client-qa.mjs
```

确认当前完整候选已经经 staging 并由 `harness/central-service-catalog.json` 固定。`CENTRAL_SERVICE_QA_RESOURCES` 指向包含 `central-service/<packageId>/` 的资源根，例如本项目的 `target`，不是单个候选目录。

```powershell
$env:CENTRAL_SERVICE_QA_RESOURCES = 'C:\Workplace\central-codex-platform\spikes\local-dev\target'
$env:CENTRAL_LIVE_QA_ALLOW_REAL_MODEL = '1'
$env:CENTRAL_LIVE_QA_AGENT = 'C:\Workplace\central-codex-platform\spikes\local-dev\target\debug\local-agent.exe'
$env:CENTRAL_LIVE_QA_HELPER = 'C:\Workplace\central-codex-platform\spikes\local-dev\target\debug\examples\central-live-client.exe'
$env:CENTRAL_LIVE_QA_OUTPUT = 'C:\Workplace\central-codex-platform\spikes\local-dev\target\central-p0\live-native-new-run\result.json'
cargo test -p central-app live_qa::native_service_real_model_local_agent_qa -- --ignored --exact --nocapture --test-threads=1
```

`CENTRAL_LIVE_QA_OUTPUT` 必须是新的 `target/central-p0/<run>/result.json`，**不是目录**；`<run>` 目录必须尚不存在，由测试原子创建。每次重跑使用新的名称，不覆盖失败记录。默认 Agent/helper 路径与上例一致，可省略这两个覆盖变量。TLS 生成使用现有 `C:/Program Files/Git/usr/bin/openssl.exe`，不用修改 hosts。

验收结束后清除本 shell 的真实调用 opt-in：

```powershell
Remove-Item Env:CENTRAL_LIVE_QA_ALLOW_REAL_MODEL
```

每次运行读取自己的 `result.json`。不能只依据 Cargo 退出码、健康检查或某一个模型回答判断通过；还须核对原生公开结果的完整证据和清理标志。

## 5. 登录后实际页面运行方法

`people_ui_qa::authenticated_people_window` 通过 `tauri/custom-protocol` 嵌入正常前端构建，而不是 Vite 开发页或复制的演示 UI。测试原生端在新的合成 profile 中完成真实服务启动、管理员登录、用户创建、合成设备配对，再显示实际中央窗口。

这个 fixture 使用正常 `Service`/`People` owner、正常 IPC 命令和正常 AppData 根；不向 renderer 注入会话，不注册产品登录后门，不返回模拟管理接口。预置设备没有 Local Agent 连接，页面必须显示离线，不能把注册记录当在线。

```powershell
npm run build --workspace @central-codex-spike/central
$env:CENTRAL_SERVICE_QA_RESOURCES = 'C:\Workplace\central-codex-platform\spikes\local-dev\target'
$env:CENTRAL_PEOPLE_UI_QA_SECONDS = '180'
cargo test -p central-app --features tauri/custom-protocol people_ui_qa::authenticated_people_window -- --ignored --exact --nocapture --test-threads=1
```

显示时间允许 30–300 秒，默认 180 秒。程序会显示实际窗口，供页面观察；不能用 headless 模块测试替代。正常关闭或到期退出都必须先确认受管服务关闭。主任务记录用户/设备列表、操作确认、配对码显示与到期、刷新/错误状态、退出过程及截图路径，具体覆盖以实际操作为准。

该测试保留唯一合成 AppData profile 供失败诊断，不能把它误记为真实账号数据或生产配置；不自动递归清理已有应用目录。真实模型验收的临时 DPAPI 清理规则不应套用成 UI fixture 的已清理结论。

## 6. 清理、失败与证据保留

真实链路测试结束时先停止/终止本次 Node Job 的进程树，再停止受管服务并核验 Job 空。只有清理已确认且路径重新解析仍指向本次 run 下的新私密目录时，才删除该临时根。清理无法确认时保留目录，并将测试标为失败；不得为了得到“通过”而抹掉失败数据。

公开 `result.json`、成功时的 `client-result.json` 及主任务记录应保留；随机原文、真实模型凭据、TLS 私钥、设备令牌不进入公开摘要。真实账号临时 DPAPI 副本、工作区和令牌库按测试清理结果确认，不根据脚本意图宣称已删除。

首次尝试曾由主任务报告原生 `CONFIG_INVALID`，当时尚未进入 Node/模型调用。该记录属于失败历史，具体修复、后续尝试及各自结果由主任务补充；不能把多次尝试合并成一次无失败通过。
