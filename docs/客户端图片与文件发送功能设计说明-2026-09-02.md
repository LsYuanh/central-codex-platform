创建日期：2026-09-02  
更新时间：2026-09-03  
文档状态：附件 MVP 已实现，Windows 真实中央链路通过；macOS 实机验收待完成

## 1. 最新需求与方案结论

本节以 2026-09-03 用户确认的需求为准，替代初版中“前端直接上传附件、中央临时附件服务、网络共享挂载”之间的待选方案。

已确定：

- 使用现有 Local Agent，不引入 SMB、NFS、SSHFS 或客户端入站文件服务；用户不需要设置共享目录。
- 拖拽或选择后，图片仍以缩略图展示，普通文件仍以文件卡片展示；发送后的消息和恢复的历史也保留附件形式，不能变成一串路径文本。
- 路径是客户端内部处理和传输使用的信息，不自动写入输入框正文。用户不需要手工把图片或文件转换成路径。
- 点击发送时，由客户端发送流程完成校验、真实路径解析、剪贴板附件准备和附件引用构造，再提交中央网关；需要的本机文件读写或图片处理由 Local Agent 执行。
- 对磁盘上已有的图片和文件，客户端发送完整绝对路径及附件元数据，不预先把整个原文件上传到中央附件仓库。
- 中央通过 Device Broker 将读取、解析或修改请求交给该客户端的 Local Agent；Local Agent 在客户端实际执行。
- 支持 Windows 和 macOS 本机绝对路径；目标是访问 Local Agent 运行账号可访问的本机文件，不再把附件限定在现有单一 workspace 内。
- 当前面向受信局域网，复杂认证、细粒度审批、多用户安全隔离暂不作为本功能上线前置条件。
- “完整访问”不代表自动取得管理员/root 权限，不绕过操作系统权限、文件锁或 macOS 隐私授权。
- 文件内容在需要时仍会通过网络返回中央用于推理。发送路径不等于模型已经读取文件或看到图片。
- 2026-09-03 已按本方案实现附件 MVP，具体范围、限制与证据见[实施与验收记录](客户端附件MVP实施与验收-2026-09-03.md)。后文分阶段计划作为设计基线保留，不代表全部验收已完成。

推荐主链路：

```text
Tauri/React：拖拽/选择 → 图片缩略图、文件卡片（本地草稿）
        │ 点击发送：客户端校验和转换为完整路径 + 附件引用
        │ （设备由连接/Thread 绑定，界面继续保留附件形式）
        ▼
中央网关 / Device Broker ← 中央 Codex/App Server 的工具请求
        │ 通过 Local Agent 已建立的出站连接下发请求
        ▼
客户端 Local Agent：读取、解析、文件修改、命令执行
        │ 返回文本 / 图片内容 / 执行结果
        ▼
中央网关适配为模型输入或工具结果 → 中央 Codex/App Server
```

中央决定做什么，Local Agent 在客户端执行。中央不挂载客户端目录，不把客户端路径当作中央本地路径打开。

## 2. 当前实现与需要改变的部分

以下是检查现有代码得到的基线，不是已完成的附件能力。

| 部分 | 当前状态 | 本次需求所需变化 |
|---|---|---|
| 输入框 | `sendTurn` 仅发送 `input: [{ type: "text", text }]` | 增加图片缩略图、文件卡片及点击发送时的客户端附件处理 |
| 消息数据 | 已有 `id/role/content/createdAt`，没有附件字段 | 保存附件元数据并支持 Thread 恢复 |
| 网关 | 转发 `conversation.turn.create`；没有附件处理流程 | 解析附件引用、定位设备、准备图片、转发设备文件工具 |
| Local Agent | `workspace/list`、`read_file`、`exec` | 支持绝对路径、文件元数据、分段读取、图片读取及后续写入 |
| 路径解析 | 拒绝绝对路径，限制在配置 workspace 内 | 在受信局域网模式支持账号可访问的本机绝对路径 |
| 文本读取 | UTF-8，文件上限 1 MiB | 增加编码错误、分页/分段、截断状态 |
| AgentRPC | 当前帧上限 1 MiB | 增加兼容协商、分块传输或专用流式能力 |
| Tauri | 管理 Agent 启停；尚无附件导入 IPC | 增加原生路径获取、元数据/预览及剪贴板数据交给 Agent 的机内通道 |

现有文档中的“仅允许 workspace 相对路径”描述是旧实现事实，不应作为新附件需求的最终限制。实施绝对路径能力时，需要同步更新 README、AGENTRPC 和相关测试；本次没有修改这些文件。

## 3. 路径语义与设备识别

### 3.1 完整路径是交给 Local Agent 的地址

支持的路径示例：

- Windows：`C:\Users\developer\Desktop\设计图.png`、`D:\项目\需求.docx`。
- macOS：`/Users/alice/Desktop/设计图.png`。

网关按连接或 Thread 中保存的设备关联定位 Agent。相同字符串可能存在于不同设备，因此只保存路径、不保存设备关联是不够的；该关联是正确路由的需要，不依赖复杂认证系统才可实现。

中央必须保留客户端路径原意，不得使用中央 macOS 的路径函数解析 Windows 盘符、拼接中央工作目录或改写分隔符。路径规范化、文件是否存在及实际权限由目标 Agent 使用本机操作系统处理。

### 3.2 访问范围

新需求允许受信局域网模式访问 workspace 外的本机绝对路径；workspace 可以继续作为相对路径和命令的默认工作目录。

- 不要求每个附件先复制进 workspace。
- 不要求用户给每个目录设置 SMB 共享。
- 不默认启动管理员/root Agent；权限不足时返回明确错误。
- `C:foo` 不是完整 Windows 绝对路径，应拒绝或要求补全。
- `~`、环境变量等不由中央猜测展开；UI 或 Agent 应转换为明确路径。
- 网络 UNC 路径、其他网络卷不作为本次必须支持的范围。
- 非文件对象和不支持的目录附件应明确提示；符号链接、快捷方式的处理需要在元数据中区分。

“可以访问文件”不等于每次添加附件都应修改它。读取、写入、删除和执行应有明确操作类型，按用户任务决定。

## 4. 文件与图片的完整流程

### 4.1 已有文本、代码及普通文件

1. 用户选择或拖拽文件后，输入框附件区展示文件图标、文件名、类型、大小和移除按钮；正文不追加路径。“添加本地路径”仅作为可选辅助入口。
2. 选择结果中已有的元数据可直接展示；需要补全时，UI 经 Tauri 的本机 IPC 请求 Local Agent 查询。选择和预览阶段不把附件路径、元数据或内容发送到中央。
3. 点击发送时，客户端固定本次正文和附件列表，由 Local Agent 复核真实路径、文件状态和必要元数据，构造附件引用后提交；不默认提交整个文件内容。界面中的文件卡片不变成路径文本。
4. 网关把附件清单提供给中央模型，并确保清单关联到当前设备和 Thread。
5. 模型需要内容时调用设备工具，Local Agent 分段读取文本或执行适用的本机解析。
6. 需要修改时，中央发出具体写入/补丁请求，Local Agent 修改客户端原文件并返回实际结果。

仅附加引用与“内容已读取”必须在界面状态上区分。普通文件的读取失败可以作为工具失败回传，不能显示为已读取成功。

### 4.2 图片：路径输入，内容送入模型

图片采用“本地展示，点击发送后启动处理，经 Agent 提供图片内容”的默认流程：

1. 拖拽或选择后，客户端显示图片缩略图、文件名和移除入口；需要读取本机图片才能生成预览时，通过本机 IPC 交给 Local Agent，不先传中央再取回预览。
2. 用户点击发送后，客户端校验附件并构造完整路径和元数据引用，提交中央网关；这是界面附件向传输数据的内部转换，不改写用户看到的正文和缩略图。
3. 网关在开始 Turn 前请求 Local Agent 读取图片；必要时由 Agent 解码、缩放和重新编码。本机读取和图片处理不在中央执行。
4. Agent 按帧限制返回图片数据；网关在有上限的内存中组装。
5. 网关将图片数据适配为中央 App Server 支持的图片输入，与用户正文一起提交。只有路径引用不能替代此步骤。
6. 收到中央提交成功确认后，UI 才标为已发送；不把传输成功等同于模型已经完成图片理解。消息中继续显示图片附件。

图片读取、传输或模型能力验证失败时，不应悄悄退化为只发文件名；保留待发送草稿并提示原因。

后续回合要重新查看图片时，可扩展返回结构化图片内容的设备工具；该工具能力也必须针对部署版本验证，不能把 Base64 字符串包在普通文本工具结果里当作视觉输入。

### 4.3 剪贴板图片：没有路径时先在客户端落盘

截图粘贴一般只有图片数据，没有可复用的原文件路径，因此是“只发路径”流程的特殊入口。粘贴后先使用内存数据展示缩略图，点击发送时再由客户端协调 Agent 生成可引用的临时文件。

推荐：

```text
剪贴板图片数据 → 客户端内存缩略图（待发送）
  → 点击发送，Tauri 接收待发送数据
  → 仅机内 IPC 交给 Local Agent
  → Agent 写入客户端应用专用临时附件目录
  → 返回绝对路径
  → 复用图片读取/发送流程
```

拟新增的机内通道可采用 Windows 命名管道 / macOS Unix domain socket 等方式；具体实现需要单独验证，不是现有能力，也不要求开放客户端局域网入站端口。

- 临时文件由 Local Agent 创建、读取和清理，Tauri 负责 UI 和数据桥接。
- 临时附件使用随机文件名，避免覆盖用户文件。
- UI 取消未发送附件时可清理对应临时文件；用户磁盘上的原文件不随附件移除而删除。
- 已发送临时附件需要保留策略，以支持历史预览和重新读取；不能一发送完就删除。
- 只清理 Agent 自己登记的应用临时文件，不清理普通用户文件。

### 4.4 PDF、Word、Excel 等文件

可以先附加完整路径和元数据；“能够附加”与“能够正确解析”是两个不同能力。

解析在客户端执行，由 Local Agent 调用已经部署并验证的本机解析器或命令，返回分页文本、表格片段、必要的页面图片和来源信息。中央不建立通用原文件仓库，也不在中央执行客户端文档解析命令。

缺少解析器、格式不支持、文件加密或解析失败时，应返回明确状态，不把二进制文件强行按 UTF-8 读取，不自动安装依赖或执行文档中的宏。

第一批优先完成图片和文本/代码文件，PDF/Office 解析与文件修改按后续阶段扩展。

## 5. 协议设计与兼容性

### 5.1 平台附件引用

以下结构是拟新增的平台协议，不是现有 App Server 原生字段：

```ts
type AttachmentRef = {
  id: string;
  source: "localFile" | "clipboardTemp";
  path: string;                 // 客户端绝对路径
  kind: "image" | "text" | "document" | "unknown";
  name?: string;
  mimeType?: string;
  bytes?: number;
  modifiedAt?: string;
};

type ConversationTurnPayload = {
  threadId: string;
  clientMessageId: string;
  input: Array<{ type: "text"; text: string }>;
  attachments: AttachmentRef[];
};
```

模型、推理强度等现有设置字段继续保留。设备关联由网关根据连接/Thread 补全，历史附件记录保存该关联。

网关必须消费并移除平台专有 `attachments/clientMessageId` 等字段，再构造部署版本支持的 App Server 请求，不能把新增字段原样透传给旧 App Server。消息关联 ID 的适配和重试语义也需验证；有 ID 并不自动意味着上游支持幂等提交。

模型收到的附件清单应包含附件 ID、文件名、客户端路径、类型和来源说明。附件内容属于用户提供的资料，不能提升成网关的系统/开发者指令。

### 5.2 Local Agent 能力

下面的方法名是设计示例，实施时统一落入现有 AgentRPC 类型、Schema、网关映射和 Agent 分发，不另建产品入口：

| 能力 | 拟定方法示例 | 返回与用途 |
|---|---|---|
| 文件元数据 | `file/stat` | 路径、大小、修改时间、类型 |
| 文本分段读取 | `file/read_text` | 文本、编码、截断标记、下一位置 |
| 图片读取 | `file/read_image` | MIME、尺寸、编码数据或传输 ID |
| 二进制分块读取 | `file/read_chunk` | 传输 ID、偏移、块序号、结束标记 |
| 文档解析 | `file/extract_document` | 页码/工作表定位及内容片段 |
| 文件修改 | `file/apply_patch`、`file/write` | 修改结果、实际路径、版本信息 |
| 剪贴板导入/清理 | 本机附件 IPC | 客户端临时路径、引用状态 |

中央动态工具映射到这些设备能力；写入和删除不作为添加附件的自动动作。超时后的写操作结果需要查询，不自动重复执行。

保持现有相对路径调用兼容。新增绝对路径、图片和分块能力应通过 Agent 能力声明协商；连接旧 Agent 时显示“需要升级 Local Agent”，不能悄悄回退到中央本地文件操作。

### 5.3 图片输入的协议边界

2026-09-02 评估引用了以下官方定义；这些链接指向可变版本，实施时必须重新核对中央机实际部署版本：

- [UserInput 定义](https://raw.githubusercontent.com/openai/codex/main/codex-rs/app-server-protocol/schema/typescript/v2/UserInput.ts)
- [App Server 用户输入示例](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md#example-start-a-turn-send-user-input)

拟验证的图片输入适配格式：

```json
{
  "type": "image",
  "url": "data:image/png;base64,..."
}
```

客户端完整路径只交给 Local Agent，不能填进中央 App Server 的 `localImage.path`。前次评估的输入联合没有普通 `file` 类型，因此文件引用由平台和设备工具承载，不虚构 App Server 原生文件输入能力。

当前方案不使用 `thread/inject_items` 绕过普通输入流程，也不依赖中央图片临时路径。

## 6. 大小、传输和磁盘占用

### 6.1 路径不是“零传输”

客户端先发送很小的路径和元数据；真正读取时仍需传输文本片段、图片或解析结果。大文件应按需读取，不默认整文件进入消息上下文。

当前 AgentRPC 帧上限为 1 MiB，不能将几 MiB 的 Base64 图片放进单个现有帧。需要在原协议内设计分块或协商新的有界流式能力，包含传输 ID、块序号、总字节数、完成/取消标记，并为断线和资源释放定义终态。

建议首轮验证使用：

- 图片原始大小上限 5 MiB、每回合图片总量上限 10 MiB，作为待实测参数，不是现有能力。
- 二进制块可从 256 KiB 起验证，给 Base64 编码和 JSON 包装留出帧空间。
- 网关设置单传输及并发总内存上限；Agent 解码图片另设像素/尺寸限制。
- 对整个文件的校验可在实际读取时进行，避免仅添加大文件就扫描全部内容。
- 开始读取与结束时核对版本信息，文件变化时重试或报错，不混合不同版本的块。

### 6.2 中央机磁盘

本方案不新增中央原文件附件仓库，不要求完整原文件先上传、落盘后再开始推理。网关只在有界内存中暂存必要的图片/文本内容，完成、失败或取消后释放。

但不能承诺中央磁盘零增长：

- App Server 的历史、缓存或内部实现可能保存返回的文本和图片内容。
- 平台会保存必要的附件元数据及 Thread/消息关联。
- 客户端原文件保留在客户端，不等于其内容不会进入中央历史。

应在真实中央机测量发送前后的历史和缓存变化；不得仅凭“网关没有写文件”就宣称没有磁盘占用。日志不输出完整 Base64 或文件正文，避免无意义的大量存储。

### 6.3 客户端临时附件

普通文件采用实时引用，不默认复制原文件。剪贴板图片需要客户端临时存储，清理策略必须区分待发送、已发送和已过期状态。

已发送临时附件的保留时长和容量是待实施确定的产品参数。历史中引用的文件已删除或临时附件已过期时，显示“源文件不可用/附件已过期”，允许用户重新选择；不从中央同名路径查找替代文件。

## 7. UI、历史与错误状态

### 7.1 入口与展示

- 附件按钮、文件拖拽、剪贴板图片和“添加本地路径”共用一个附件列表。
- 图片使用缩略图展示；普通文件使用文件图标、文件名、类型和大小展示。附件排列在输入框附近的独立附件区，用户正文保持原样。
- 拖拽/选择后不得用完整路径替换附件卡片，不得把路径自动拼入正文。内部保存路径与界面显示附件是两套表示，同一个附件 ID 将它们关联起来。
- 原生文件选择/拖拽需获得真实完整路径；普通 HTML file input 通常不会提供真实绝对路径，不能使用 `C:\fakepath\...` 作为地址。
- 使用 Tauri 原生路径能力，不在前端新增一套任意文件操作实现；实际读取交给 Agent。
- 本机图片预览由 Agent 通过本机 IPC 返回，剪贴板预览可直接使用内存数据；UI 临时持有预览 URL，释放时撤销 URL，不把 Base64 长期放入 localStorage。
- 选择文件只登记本地草稿并准备必要预览，不自动上传、不自动发送、不开始 Turn；正文为空但有有效附件时可以发送。
- 用户文件的移除按钮只移除引用；不会删除本机原文件。
- 显示文件名、类型、大小，悬停可查看完整路径和来源设备。
- 发送成功后的对话消息继续显示图片缩略图和文件卡片，Thread 恢复后保持相同展示；图片预览暂不可用时显示带文件名的占位卡片，不能只剩路径文字。
- UI 提示内容会经中央推理链路处理，不要求每次附件走复杂审批。

### 7.2 点击发送时的客户端处理

客户端发送流程负责从可视附件生成协议数据，用户不参与这一步转换：

1. 固定本次正文和附件 ID 列表；处理期间阻止重复点击发送，避免附件与正文错配。
2. 通过 Tauri/Local Agent 获取和复核真实路径、类型、大小以及文件可用状态；剪贴板图片此时通过 Agent 写入客户端临时文件。
3. 构造正文与结构化附件引用，不把文件路径或图片 Base64 直接塞入可编辑正文。
4. 提交中央网关，随后按本文图片准备或文件按需读取流程继续。客户端处理不取消网关协议适配，也不允许网关把客户端路径当中央路径读取。
5. 保留原来的缩略图/文件卡片和正文，直到收到提交确认；处理或提交失败时保留草稿并提供重试、移除入口。

“发送的时候客户端做处理”不表示拖入文件时就读完整正文、解析大型文档或上传全部字节。添加阶段只做本地展示所需的工作，发送阶段做校验与转换，文件内容再按类型通过 Agent 提供。

### 7.3 状态和恢复

至少区分：

```text
已拖拽/选择 → 本地缩略图或文件卡片 → 等待用户点击发送
点击发送 → 客户端校验/路径与引用转换 → 提交中央网关
图片：Agent 准备图片 → 传输中 → 提交 Turn → 已发送（保留图片展示）
普通文件：引用已发送（保留文件卡片）→ 模型请求读取 → 已读取/读取失败
```

失败均有原因和恢复入口：Agent 离线、文件不存在、OS 权限不足、路径无效、编码/解析不支持、超出大小、传输超时、源文件变化、模型不支持图片、Turn 提交失败。

图片准备失败保留草稿；普通文件明确显示仅引用还是已读取。断线后可恢复只读操作，但 Turn 提交结果未知时先核对历史，不能盲目重发造成重复消息；写入/删除也不自动重试。

### 7.4 历史模型

在现有消息数据上增加附件数组和来源设备关联，例如：

```ts
type MessageAttachment = AttachmentRef & {
  deviceId: string;
  state: "referenced" | "read" | "failed" | "unavailable";
};

type ChatMessage = {
  id: string;
  role: "user" | "assistant" | "system";
  content: string;
  attachments?: MessageAttachment[];
  createdAt?: string;
};
```

设备 ID 用于稳定定位原文件，不能在切换设备后把相同路径解释为另一台机器的文件。Thread 恢复需要平台附件元数据与 App Server 消息关联；不能假设 App Server 会自动保存并返回所有平台自定义字段。

原文件修改后，历史预览重新读取可能反映新版本；需显示文件变化，不能宣称是发送时快照。需要快照的后续场景，应由 Agent 在客户端生成副本并定义保留策略。

## 8. 阶段边界

当前确认的受信局域网阶段不要求先建设完整认证、mTLS、逐文件审批、病毒扫描或生产级多租户隔离，也不继续把 SMB 或中央附件仓库列为待选主方案。

仍需实现正常运行所必需的：

- 正确设备路由和客户端原生路径解析。
- OS 权限错误、文件锁和文件变化处理。
- 帧/内存/解码上限、超时、取消和失败终态。
- 源文件与应用临时文件的清理边界。
- 原有 Local Agent 随桌面启停的生命周期。
- 真实中央链路验证，不用 Fake Central 成功替代验收。

服务继续只用于当前局域网，不新增公网暴露。未来扩展生产认证与权限时，应保留协议演进空间，但不把这些能力强行加入本次附件 MVP。

## 10. 验收清单

- [ ] 不配置任何 SMB 共享或客户端入站网络服务即可使用。
- [ ] Windows/macOS 的 workspace 外本机完整路径均能通过对应 Agent 读取。
- [ ] 同名路径在不同设备之间不会误路由；断线不会回退到中央本地文件访问。
- [ ] 选择/拖拽获得真实绝对路径，不发送 fakepath。
- [ ] 拖拽/选择图片显示缩略图、文件显示文件卡片，不将附件变成正文中的路径文本。
- [ ] 点击发送前仅本地预览，不向中央发送附件路径、元数据或内容，不启动 Turn。
- [ ] 点击发送后由客户端自动校验并转换附件引用，无需用户手工处理路径；失败保留草稿且不重复提交。
- [ ] 已发送消息及历史恢复仍保持图片/文件附件展示；预览不可用时有文件名和占位卡片。
- [ ] 普通文件先发送引用，模型通过 Agent 获取内容；不默认整文件落中央磁盘。
- [ ] 图片经 Agent 读取后真正进入视觉输入，而非只提交路径或 Base64 文本。
- [ ] 剪贴板图片由 Agent 保存到客户端临时目录并复用相同流程。
- [ ] 大图片不会突破现有 1 MiB 帧限制；传输中断和取消后资源可释放。

- [ ] Thread 恢复能还原附件元数据；设备离线/文件过期时显示可恢复状态。
- [ ] 实测并记录中央内存、历史和缓存增长，不承诺未经验证的零磁盘占用。
