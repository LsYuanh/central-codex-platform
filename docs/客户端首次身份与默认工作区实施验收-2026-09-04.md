# 客户端首次身份与默认工作区实施验收

日期：2026-09-04。

## 实现结果

新打包客户端不再把 `userId=desktop-user&deviceId=desktop-device` 写入默认网关。首次启动无保存配置时，设置页自动预填以下内容：

- 用户 ID：当前操作系统账号名，无法取得时使用带安装 UUID 短段的回退值；
- 设备 ID：规范化电脑名加持久化安装 UUID 的首段；
- 本机工作区：Windows“文档/Codexia Workspace”，macOS `~/Documents/Codexia Workspace`；
- 中央网关：`ws://192.0.2.10:4510/ws` 基础地址，不保存身份查询参数。

用户 ID、设备 ID 和工作区都可编辑。UI 用用户 ID 和设备 ID 组装 `/ws` 地址；Local Agent 用设备 ID 组装 `/ws/agent` 地址。首次“保存并应用”前，桌面不连接中央、不启动 Local Agent，也不创建默认工作区。保存系统建议的默认路径时才创建该目录；用户填写的其他不存在目录仍返回明确错误。

本机工作区是 Local Agent 浏览文件和执行命令时的默认根目录。相对文件路径与相对命令工作目录从这里解析。选择或保存工作区不会自动上传目录内容，中央机也不会把它当作自己的工作目录；实际系统操作仍由客户端 Local Agent 执行。

升级兼容策略是保留已有配置。旧网关 URL 中的 `userId`、`deviceId` 会迁移到独立字段，其他查询参数保留；已有工作区不重置。因而老用户仍可能在设置页看到 `desktop-user` / `desktop-device`，直到主动修改。Local Agent 对旧 `desktop-device` 的持久化设备键兼容逻辑继续保留。

- `spikes/local-dev/apps/desktop/src-tauri/src/runtime.rs`：身份生成、URL 迁移/组装、首次门控、默认目录创建和进程测试；

- `spikes/local-dev/apps/desktop/src-tauri/Cargo.toml`、`Cargo.lock`：UUID 与平台电脑名依赖。

## 验收边界与后续

当前 Codex 桌面运行在 Windows MSIX 环境中，NSIS 安装目录和 Tauri 配置目录会发生 LocalCache 虚拟化/合并视图。为避免改坏用户原配置，本轮在目标 release 二进制上验证设置 UI，在独立进程测试中验证首次门控、自动建议值和目录创建；没有把该机器上保留旧配置的界面冒充全新独立系统首次安装截图。原运行配置已恢复且哈希一致。

向 `operator@192.0.2.10` 同步本次 6 个私有源码文件曾被自动审批拒绝。用户明确授权具体文件和目标目录后完成同步；本机与 Mac 的 SHA-256 逐一一致。Mac 已重建 DMG，并通过编译、首次配置进程专项、镜像校验和包内 Agent 真实设备验证。

真实设备文件读取 smoke 最初也被自动审批拒绝，因为脚本会读取测试工作区 `README.md` 并通过局域网网关回传内容。用户明确允许该传输后执行成功，没有使用其他通道绕过审批。进程、静态检查、UI 和设备验证均未创建模型 Turn。
