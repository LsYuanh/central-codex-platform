## Windows 隔离实测

最新完整系统调用证据：`spikes/local-dev/target/central-p0/full-joblimit-4/`。

- 进程 token 确认为 AppContainer，本用户合成文件读写成功。
- 中央 canary 读写、其他用户文件读取、指向中央 canary 的硬链接读取均返回访问拒绝 5。
- 父进程专用环境变量未继承；创建子进程返回 Job 配额限制 1816。独立 AppContainer 对照取消 Job 数量上限后，子进程创建成功并观察到 ready，随后明确终止回收。
- 关闭 Job 前确认 holder 活跃；关闭后等待退出成功，AppContainer profile 清理成功。
- Loopback 连接只观察到超时 10060，**不视为网络隔离证明**；尚未覆盖 LAN、公网、DNS、IPv6 的完整拒绝矩阵。
- 三个标准管道在合成 AppContainer 进程中可以通信。另一个设为可继承、却未加入允许列表的 canary 句柄在子进程中返回 `STATUS_INVALID_HANDLE (0xc0000008)`；此项通过，不等于穷尽所有句柄覆盖。

单独加上 `PROC_THREAD_ATTRIBUTE_CHILD_PROCESS_POLICY` 会使本机探针在入口前以 `0xc0000142` 退出；当前原型使用已经实测的 Job 活跃进程数上限 1。没有修改交互桌面 ACL、全局防火墙或 loopback exemption。

CRT-free loader 的 `WINDOWS_LOADER_PROBE_OK` 仅证明进入该诊断入口，不算完整隔离或真实模型验收。带遗漏句柄 canary 的合成 stdio 证据为 `spikes/local-dev/target/central-p0/ipc-fixture-7/runtime-verified.json`，明确标记 synthetic；无 Job 上限的子进程对照在 `spawn-baseline-1`。

### 真实 App Server 启动阻碍

`real-runtime-1` 已在 AppContainer 内启动实际构建的二进制，复制后的 SHA-256 与构建记录一致，但初始化前因 `failed to canonicalize CODEX_HOME ... 拒绝访问 (os error 5)` 退出。`real-runtime-2` 改用一次性 AppContainer profile 的独立 LocalState 空目录后仍失败。两次 profile 均已清理；未读真实凭据，未运行模型。

固定源码 `codex-rs/utils/home-dir/src/lib.rs` 先读取目录 metadata，再调用 `std::fs::canonicalize`；错误发生在后一步。暂不能把问题定性为工作区 ACL，也不能通过删除规范化校验宣告验收通过。本轮真实初始化 marker、中央命令/文件 RPC 拒绝尚未获得成功证据，合成 fixture 不替代此项。最小 API 诊断及后续边界见 [Windows 探针说明](../spikes/local-dev/harness/windows-probes.md)。

合成诊断在工作区自有目录与一次性 profile 目录得到相同结果：metadata 和 `CreateFile(FILE_READ_ATTRIBUTES)` 成功；`GetFinalPathNameByHandle` 的 `NORMALIZED/OPENED + VOLUME_NAME_DOS` 均返回 5，而 NT 与无卷名前缀的对应模式均成功。证据为 `ipc-canonical-workspace-1`、`ipc-canonical-profile-1`。因此本机失败集中于 DOS 卷名形式获取，尚未确定更底层原因；后续应评估受限 Windows 路径适配，保留规范化及目录边界检查。

先完成 Windows 运行前提，再接中央 UI。当前 `worker-isolation.ts` 继续拒绝 Windows，不能把探针接入正式路径后直接宣布支持 Windows 中央机。

1. 已完成 AppContainer 下 `CODEX_HOME` 修复、真实隔离初始化 marker 和中央命令/文件 RPC 拒绝验证；后续运行验收继续保留这些门槛。
2. AppContainer 与模型代理的命名管道、每租约 TLS、实例/PID/SID 绑定和流式取消已在独立 QA 中实现并验证；下一步接入正式 Windows Worker 生命周期与凭据配置，不能直接把 QA 启动器当作产品运行入口。
3. 双真实 Worker 的并发与租约撤销 QA 已通过；继续补齐完整网络拒绝、继承句柄与正式多用户运行边界。模型秘密仍由中央代理持有。同机真实模型 → QA 路由 → Local Agent 已通过；正式网关 → 独立目标设备仍须完整验收。
4. P0 运行门槛通过后，P1 再实现 `apps/central` 原生配置、预检及受管进程生命周期，随后接入运行概览。用户、配对、模型管理和双平台安装包按原计划推进。

前序 Windows RC4 客户端链路已通过的结论来自既有交接，本批未重跑；Mac RC4、安装升级与回滚仍保持未完成。本批只读检查正式 4510 健康端点得到 `ok=true`，这不属于新 Windows 中央运行验收。
