# Windows 模型管道接入与验收

日期：2026-09-10。本轮继续中央管理 App 的 Windows P0，范围为模型代理受限 IPC。代码进入既有 `spikes/local-dev`；正式 4510 服务和已安装客户端没有替换。

## 通信与身份边界

Windows AppContainer 内的真实 App Server 使用固定 `https://model-broker.invalid/v1/responses`，底层连接该 Worker 的本地命名管道。父启动器预建四个管道实例，核验每条连接的 Worker PID、AppContainer token 与 SID 后，才将原始字节转发到预先指定的中央代理 HTTPS 端口。

TLS 在这条实际连接内握手。中央代理为每个 Worker 租约生成独立 CA 和服务端密钥；Worker 只收到该租约的公开 CA 和受限 token。Rust 客户端仅信任该 CA，不启用系统根证书、HTTP 代理、重定向、连接重试、WebSocket 或 TCP 回退。模型 URL、方法及关键请求头逐请求检查。真正的模型账户凭据仍留在中央代理。

代理 HTTPS 入口绑定特定租约；其他 Worker 的 token 及通用 HTTP 入口绕过均被拒绝。撤销租约时关闭连接、终止上游请求并释放并发额度。证书握手错误只记录固定诊断类别，不记录 token、模型正文或私钥。

命名管道的 `GENERIC_WRITE` 包含创建额外实例的权限，因此四个实例必须在 Worker 恢复前全部预建并保留句柄，连接结束仅 Disconnect 后复用。首次实例创建失败时终止 Worker；不能把随机名称或一次服务端 PID 预检查当作实际连接的 TLS 身份验证。详细原生证据见 `spikes/local-dev/harness/windows-model-pipe.md`。

## 真实隔离运行时与合成模型链路

最终 7 组全部通过，原始证据 `spikes/local-dev/target/central-p0/model-runtime-2/result.json`；可提交的脱敏归档为 `spikes/local-dev/harness/verification/windows-model-runtime-2026-09-10.json`。

| 场景 | 实测结果 |
|---|---|
| 初始化与宿主边界 | 真实 marker 正确；command、filesystem、skills RPC 拒绝；工作区覆写拒绝 |
| 模型/工具循环 | 3 次模型请求，内置 exec 越界调用拒绝，1 次合成设备动态工具调用返回，Turn 完成 |
| 静默流中断 | Turn 为 interrupted，5 秒内上游关闭，没有自动重放；随后新 Turn 正常完成 |
| 正常请求总数 | 管道连接、TLS 成功、HTTP 请求、合成上游请求均为 5 |
| 输出尾部 | 首轮与恢复轮各 131123 个 UTF-8 字节，SHA-256 均与含中文尾标的 fixture 一致 |
| EOF 排空 | 正常 EOF 尾部排空 3 次；本轮无需取消排空；独立系统调用探针另有阻塞取消证据 |
| 错误 CA | 1 次实际管道连接；TLS 成功、HTTP 请求、上游请求均为 0；Turn 明确携带 `MODEL_PIPE_TLS_CERTIFICATE_REJECTED` 并失败 |
| 生命周期 | 正常与错误 CA 两个 Worker 均完成 Job 回收、profile 清理及 TLS 租约关闭 |

首轮 `model-runtime-1` 正常链路通过，但错误 CA 仅显示泛化失败，严格负例判据未通过。最终通过新增的类型化错误诊断取得明确证据；没有把连接失败或零请求单独当作证书拒绝。最终服务端仍只报告泛化 TLS 握手失败，证书拒绝结论来自 Rust 实际错误类型。

排空修复也不是固定等待：上游正常 EOF 后，桥等待 `FlushFileBuffers` 确认已写管道数据被读取；等待、取消、线程回收均有上限，异常路径不 detach 仍引用栈数据的线程。独立探针 5 项通过，归档 `spikes/local-dev/harness/verification/windows-pipe-flush-2026-09-10.json`。客户端全关闭、TLS reset 和中断仍快速取消。

运行时 stderr 中唯一正常链路日志为预期的 `unsupported call: exec_command`，来自注入的越界工具负例；错误 CA 运行时 stderr 为空。测试结果中的 `stderrBytes` 是父 launcher 的 stderr，不能将其与 Worker 日志混同。

运行命令（先加载 MSVC x64 编译环境，完整操作示例见 harness README）：

```powershell
node spikes/local-dev/harness/windows-model-smoke.mjs --launcher C:/Workplace/central-codex-platform/spikes/local-dev/target/central-p0/windows-isolation-probe.exe --runtime C:/Workplace/central-codex-platform/target/p0w/target/debug/codex-app-server.exe --output C:/Workplace/central-codex-platform/spikes/local-dev/target/central-p0/NEW_MODEL_QA
```

## 完成边界

本轮受限模型 IPC 的实现及合成链路验收完成，仍为 `deployable=false`。随后已单独完成真实模型到同机 Local Agent、受控 LAN 拒绝和自然租约到期验收，见 [真实模型联调](Windows真实模型与Local-Agent联调-2026-09-10.md)。Windows 正式 Worker 启用、模型账户配置/秘密存储、loopback/完整网络拒绝、安装生命周期及中央管理界面仍需独立完成。

后续用户已明确选择本机现有 Codex 登录，QA 中央代理只读原登录文件，为独立 Worker 发放短期租约；未复制或修改账户凭据。真实联调修复了成功完成 SSE 后断开被误审计为取消的问题；最新 HTTPS 租约回归为 19 项。既有中央健康端点只读检查为 `ok=true`，不代表新 Windows 运行时已部署到该服务。
