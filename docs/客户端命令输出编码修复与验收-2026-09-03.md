# 客户端命令输出编码修复与验收

日期：2026-09-03。Windows 修复已进入现有 Local Agent，并更新试用安装器。

## 问题与实现

搬迁后的桌面 Agent 启动 Windows PowerShell 5.1 时，默认命令输出为本机 OEM 代码页
CP936；原实现直接 `String::from_utf8_lossy`，导致中文 cwd 和错误信息出现乱码。

新模块 `spikes/local-dev/crates/local-agent/src/command_output.rs` 统一处理 stdout/stderr：

- 优先识别合法 UTF-8，移除 UTF-8 BOM，识别带 BOM 的 UTF-16LE/BE。
- Windows 无 BOM 且不是有效 UTF-8 时，通过 `GetOEMCP` 与 `MultiByteToWideChar`
  严格转换；本机实测代码页为 936。UTF-8 BOM 明确存在时不猜测 OEM 编码。
- 截断避免切开 UTF-8 字符、UTF-16 代理对和 Windows 双字节字符。
- 原始前缀及返回 UTF-8 字符串均保留每流 64 KiB 上限；转码扩张超过限制也报告
  `truncated`。该限制约束响应，不改变原有命令捕获内存策略。
- 成功与非零退出错误使用同一解码，不改调用参数、机器代码页或文件内容协议。

仅新增 Windows 条件依赖 `windows-sys/Win32_Globalization`。中央只路由请求，实际
PowerShell/cmd 及字节转换都在 Windows 客户端 Agent 执行。

不是所有编码都能自动识别：无 BOM 的字节同时符合 UTF-8 和 OEM 时优先 UTF-8；
混合编码、自定义代码页和无 BOM UTF-16 仍可能不可读。工具显式输出 UTF-8 最可靠。

转换依据：[Microsoft MultiByteToWideChar](https://learn.microsoft.com/en-us/windows/win32/api/stringapiset/nf-stringapiset-multibytetowidechar)。

## 验证

| 检查 | 结果 |
|---|---|
| `cargo fmt --all -- --check` | 通过 |
| `cargo test -p local-agent --locked` | 13 项通过，含 UTF-8、BOM、CP936 与字符边界回归 |
| `npm run package:desktop` | Windows release Agent、桌面及 NSIS 构建通过 |
| 新 release Agent → 真实中央 `npm run device:smoke` | `DEVICE_BROKER_SMOKE_OK`，目录、文件及 Git 命令成功 |
| 新 release Agent → 真实中央 `npm run encoding:smoke` | `COMMAND_ENCODING_SMOKE_OK`，输出代码页及 OEM 均为 936 |
| 原客户端与中央服务 | 未重启，测试结束后原客户端仍在，中央 `clients=2, devices=2` |

编码 smoke 用独立设备和临时中文目录，Agent 以 detached/no-console 方式启动，避免
继承开发工具的 UTF-8 控制台掩盖问题。覆盖默认 PowerShell 中文 cwd、stdout/stderr、
cmd 中文、非零退出中文错误、明确 OEM 输出、UTF-8 emoji、UTF-16 BOM 和长中文截断。
默认命令案例没有设置 `OutputEncoding`，不以命令侧绕过作为修复证据；测试不调用模型。

复现命令见 README 的 Windows 命令输出编码段。`encoding:smoke` 总超时为 45 秒，
使用唯一设备标识，结束时关闭连接与测试 Agent 并清理临时目录。
