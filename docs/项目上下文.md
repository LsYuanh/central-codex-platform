## 1. 项目是什么

项目名“远舟”（Central Codex Platform），为多名用户提供中央化 Codex 远程工作能力。用户在 Windows/macOS 工作客户端对话，中央机运行 Codex 推理，再由用户指定电脑执行文件、Git 和命令操作。另有独立“中央管理 App”，管理中央自身的配置、模型接入、服务、用户与设备。

目前已有可用的局域网部署，重点是继续维护和完善现有产品，不是重新搭建演示原型。主要实现始终在 `spikes/local-dev/`；目录名含 Spike 不代表需要另建正式代码库。

## 2. 不可改变的架构边界

```text
工作客户端 UI ── WSS /ws ── 中央网关 ── stdio ── 按用户 Codex App Server
                                  │ 编排和路由工具请求
本机 Local Agent ── 主动出站 WSS /ws/agent
       └─ 在目标客户端执行文件读写、Git、PowerShell 和其他命令

中央管理 App ── 原生管理层 ── 中央自身配置、模型认证、网关和 Worker 生命周期
```

- Codex/App Server 和上游模型凭据只在中央，客户端不依赖本地 Codex、CLI、helper 或 App Server。
- 客户端系统操作统一由 Local Agent 执行。中央管理自己的服务不等于可以直接执行用户的客户端任务。
- 客户端仅主动出站；SSH 只用于开发人员配置和诊断中央，不进入产品链路。
- 桌面在配置就绪后自动启动 Agent，关闭时回收；安装包已内置 Agent，不要求用户手动启动。
- UI 分别显示网关连接、设备在线、Turn 运行和客户端工具执行状态。未知结果不能显示成功，也不能自动重放命令、补丁或模型任务。

## 6. 接手时的工作方式

1. 先读根 [AGENTS.md](../AGENTS.md) 和本文，再按本次任务读取相关手册与代码；仅需要追溯设计时才读长篇历史需求。
2. 检查 `git status --short`、近期提交、当前分支；以现场为准，不根据上次对话假定工作区干净或服务在线。保留其他任务的改动与已有 stash。
3. 在现有工程小范围修改；不创建平行 UI/产品目录。目录、身份、认证等已有决定若与旧记录冲突，核对最新用户要求与实现。
4. 按风险验证：UI 做 TypeScript/Vite 和实际 Tauri 检查；Rust 做 fmt/check 和相关测试；协议、生命周期、系统执行改动补对应真实链路。Fake Central 成功不替代真实中央验收。
5. 相关验证通过后仅提交本次修改到本地 Git；不默认推送、打包、安装或部署。此前发布授权不延续到新任务。
6. 更新本文受影响的摘要与对应手册，交接说明做了什么、验证范围、未完成项及本地提交。没有变化的事实不为凑更新而改写。

涉及真实部署前查[发布与回退手册](发布与回退手册.md)，不能直接修改已固定哈希的安装资源。不能把文档中的历史操作或授权当作本次部署指令。

## 8. 如何持续维护本文

本文是唯一的新对话上下文摘要，固定路径，不按日期复制新文件。控制在约 150 行以内，以当前结论替换过时结论；完整日志、逐次验收和操作细节放到对应手册或忽略的产物目录。

发生架构/关键决定、能力/代码入口、版本/部署、验收结论或未完成交接变化时，在同一任务提交中同步本文并更新日期。更新部署状态必须有实际部署证据，区分“代码已实现”“本地已验证”“已经发布”。若任务中断或有需要接续的事项，在第 7 节注明日期、做到哪里、下一步、阻塞和证据入口；完成后收敛为结论，不累积过期待办。

不记录密码、令牌、私钥、完整配对码、用户文件正文或短期 PID。不重复复制长清单与哈希；引用其权威配置/手册。文档与代码或现场不一致时明确差异并核对，不把陈旧摘要当作成功证明。
