## 构建命令

在 `spikes/local-dev/` 原生平台工作目录运行，先确认没有占用该 target 的 Cargo/Tauri 构建。

```text
node scripts/package-desktop.mjs --rc --plan
node scripts/package-desktop.mjs --rc
node scripts/package-desktop.mjs --rc --rc-version 0.2.0-rc.2
```

`--plan` 只查询 Rust host 并输出最终配置，不构建或写文件；默认构建 release。
`--debug` 仅用于调试包，不能把其结果标成 release 验收。
第二条完成并归档其安装包后，再执行第三条；禁止并行复用该 target。
macOS 当前中央 QA 主机需要在这一次命令的环境中设置
`DEVELOPER_DIR=/Library/Developer/CommandLineTools`，不得修改系统 `xcode-select`。

产物目录为 `target/desktop-rc-20260909/<host>/release/bundle/`：
Windows x64 为 NSIS，macOS 按构建机架构产出 `.app` 和 DMG。
Mac 主程序和内置 Agent 分别位于 `.app/Contents/MacOS/yuan-zhou-rc` 和 `local-agent`。
平台验收 helper 只用于开发验收，不随安装包分发。

脚本只打包客户端与内置 Agent，不内置账号、服务器 CA、TLS 私钥或工作区。
安装后仍通过现有设置、平台登录和配对连接中央；第五批只配置 4529。

## Windows 升级与卸载边界

Tauri CLI 2.11.4 的 NSIS 模板使用产品名构造卸载登记项，使用主程序名检查运行进程，
应用数据删除路径使用 bundle identifier。仅改 identifier 无法充分隔离安装器。
因此 RC 三者均独立；依据为对应版本的
[Tauri NSIS 模板](https://github.com/tauri-apps/tauri/blob/tauri-cli-v2.11.4/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi)。

RC hook 在安装、卸载的文件操作前校验标准化目录，拒绝其他目录和目标目录 junction/symlink。
这限制了 `/D=` 和安装器目录选择，不支持自定义 RC 安装位置。
本机用户目录仍是受信任的操作边界；它不是对有权修改用户目录的同用户恶意进程提供隔离。
运行中的 RC 应先正常关闭，让客户端停止自己的 Agent，再做安装升级或卸载。

RC 卸载始终保留应用配置和凭据；hook 将 Tauri 的应用数据删除状态置零并打印保留说明，
包括用户勾选“删除应用数据”的情况。这样可演练二进制回退，但**卸载不能代替退出账号、
吊销设备或原生凭据清理**；验收结束使用精确 RC 命名空间执行清理。
安装器不删除工作区或中央历史。

`rc.1 → rc.2` 应核对设置、用户、设备、证书和历史选择保持一致；版本比较与实际覆盖安装
必须用最终 NSIS 包验收，静态检查不能替代。旧 Thread 的设备/工作区绑定继续生效，
重新配对不能被当成绕过旧绑定的升级手段。

## 签名与分发状态

RC 清除继承的 `APPLE_*` 和 `TAURI_SIGNING_*` 发布凭据，Windows 未设置证书和签名命令，
macOS 指定 ad-hoc 签名 `-`，不生成 updater 产物。它们是隔离验收包，不是已签名、公证的
正式分发包。实际构建后还需记录 Windows Authenticode 和 macOS codesign/公证检查结果。
不得为运行 RC 而关闭系统签名、Gatekeeper 或 TLS 校验。

正式切换前仍需准备组织发布证书、公证及可信分发流程；本脚本不创建或申请这些证书。
当前 macOS 构建机只证明相应架构的包，不能自动宣称 Intel/Apple Silicon 均已实测。
