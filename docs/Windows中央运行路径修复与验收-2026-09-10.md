# Windows 中央运行：路径规范化修复与验收

日期：2026-09-10。用户确认本轮先修复 AppContainer 内 `CODEX_HOME` 规范化失败，再验证真实初始化和中央命令/文件 RPC 拒绝。沿用多线程开发，未部署正式中央服务。

## 问题与修复

前一轮 Windows App Server 已构建，但在初始化前因 `std::fs::canonicalize(CODEX_HOME)` 返回访问拒绝 5 而退出。目录 metadata 与打开操作本身成功；失败集中于 DOS 卷名查询。卷 GUID 查询及通过 launcher 传入 GUID 路径的对照也失败。

固定 Rust 1.98.0 实现无条件请求 DOS 路径；仅改变环境变量前缀无法消除这次查询。[固定编译器源码](https://raw.githubusercontent.com/rust-lang/rust/88d9e12ae178fab0fb5cc050a94da85685d449ea/library/std/src/sys/fs/windows.rs)

本轮在 `harness/windows_home.rs` 实现私有 Windows helper，通过独立的 `windows-home.patch` 接入固定上游 `utils/home-dir`。原始 `remote-workspace.patch`、上游提交、第三方依赖和 Mac 源码准备保持原值。

补救仅在以下条件同时满足时运行：原规范化返回错误 5、`CODEX_REMOTE_WORKSPACE=1`、实际进程 token 为 AppContainer。其余情况继续返回原结果。

1. 只接受存在的本地绝对盘符目录；以原 token 打开目录，任何权限失败继续拒绝。
2. 从已打开句柄读取 `FILE_NAME_NORMALIZED | VOLUME_NAME_NT`；不采用 OPENED、NONE 或纯字符串规范化。
3. 严格校验返回值为本地 `HarddiskVolume<数字>` 下的目录，将其转为可打开的 GLOBALROOT 路径。卷根及其他设备命名空间被拒绝。
4. 重新打开该路径，比较原、新两个活跃句柄的卷序列号和 128 位文件 ID，确认是同一目录；查询、打开或身份比较失败均不返回成功。

该路径转换保留 OS 规范化与权限检查，不改变 AppContainer、Job、网络策略或目录 ACL。它验证转换时的目录身份，不能代替 launcher 的祖先 reparse/ACL 检查，也不能保证返回后目录永远不变。[规范化 API](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew)、[文件身份 API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info)
