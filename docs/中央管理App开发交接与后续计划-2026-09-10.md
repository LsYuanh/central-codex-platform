## 1. 已确认的目标与范围

用户希望通过独立的“远舟中央管理”App 管理中央服务。Windows 或 macOS 电脑安装、完成配置后，都能实际承担中央推理和用户接入，不能只做到管理页面跨平台。

第一版范围已在本次会话确认：

| 功能 | 用户可完成的操作 |
|---|---|
| 首次配置 | 选择中央数据目录，配置监听端口与客户端连接地址，接入模型账号，完成运行检查 |
| 运行概览 | 启动、停止中央服务；查看网关、模型运行进程、在线设备和运行任务状态 |
| 用户与设备 | 创建、停用用户，生成一次性配对码，查看设备归属和在线状态，撤销设备 |
| 模型管理 | 配置模型接入，检查登录或可用状态，分配用户使用权限 |
| 设置与诊断 | 管理并发限制、查看运行日志和错误、导出诊断信息 |
| 双平台交付 | Windows、macOS 原生安装包及实际中央运行验收 |

客户端继续使用“中央地址＋一次性配对码＋设备令牌”。管理员通过中央 App 管理，客户端用户不用输入平台账号密码，也不用维护设备证书或操作钥匙串。这里简化的是使用和管理方式；模型服务仍然需要有效登录或 API 密钥，设备连接仍然需要鉴权。

第一版以管理**安装 App 的这台中央电脑**为默认范围。远程管理其他中央机、集群、自动接管、互联网部署、自动更新、历史跨中央迁移、系统服务模式暂不包含。以下技术拆分和默认交互为实施建议；若遇到无法满足已确认目标的技术限制，应记录实测结果再调整范围。

中央 App 的本地设计和开发可继续；旧 Mac RC4 收尾单独跟踪，不把旧包当作新中央 App 的交付包。

## 4. 必须保持的架构

```text
中央电脑（Windows 或 macOS）
  远舟中央管理 App
    └─ 原生管理层：配置、秘密保存、运行包检查、受管进程生命周期
         ├─ 中央网关：用户、设备、配对、Thread、路由、审计
         ├─ 中央模型访问代理：上游登录只留中央
         └─ 按用户隔离的 Codex App Server：推理与工具请求编排
                         │ HTTPS / WSS
                         ▼
客户端电脑（Windows 或 macOS）
  远舟工作客户端 ── 管理本机 Local Agent
                         └─ 执行本机文件、Git、命令和工作区工具
```

中央 App 可以管理中央自身的配置、运行数据和服务进程；用户任务所需的客户端文件读取、写入和系统命令仍由目标 Local Agent 执行。客户端主动出站，不开放入站 SSH。SSH 只用于开发和诊断，不能成为安装、启动、模型调用或设备接入的产品链路。

中央端不能通过取消隔离检查、自动切到旧模式、换成未打补丁的 App Server 或本地执行客户端命令来实现“Windows 能启动”。普通设备令牌始终不是管理员凭据，包括管理员名下的工作设备。

## 5. 建议的工程拆分

在现有 `spikes/local-dev/` 内增加 `apps/central`，作为中央管理产品入口；继续使用现有 Tauri、React 和构建方式。它是明确的新中央端角色，不复制一套工作客户端，也不复制网关、用户库或协议实现。

| 位置 | 责任 |
|---|---|
| `apps/central`（待新增） | 管理页面、原生命令边界、中央 App 生命周期 |
| `services/test-gateway`（现有） | 继续承载中央业务和管理接口；先复用，不为命名另建服务 |
| 中央运行管理模块（待实现） | 启停、健康检查、版本校验、端口冲突、配置应用和进程回收；可从原生层按职责抽取 |
| `crates/platform-security`（现有） | 复用并扩展受保护存储能力，明确中央与客户端命名空间 |
| `packages/agentrpc-types`（现有） | 设备协议；管理 DTO 另按需要抽取共享类型，避免混入设备执行权限 |
| `harness/`、`scripts/`（现有） | 固定版本构建、补丁和 QA；QA 控制脚本不能直接成为产品管理后门 |

中央 App、工作客户端、QA 包必须使用独立应用标识与数据目录。同机安装时不能互相覆盖配置，也不能因为两个角色同时运行就共享管理权限。

## 6. 管理接口与底层缺口

### 6.1 可复用接口

| 现有接口 | 可复用能力 | 接入时需要补齐 |
|---|---|---|
| `GET /healthz` | 网关存活、连接数、设备数、运行标识 | 区分“网关运行”和“模型可用”；空闲 Worker 未启动不一定是故障 |
| `POST /auth/admin/users` | 用户列表 | 对应页面、错误处理及刷新 |
| `POST /auth/admin/user/create` | 创建用户 | 当前要求密码；为仅配对用户增加明确无密码身份类型，不能生成占位密码掩盖模型差异 |
| `POST /auth/admin/user/disable` | 停用用户 | 影响提示、状态同步；重新启用用户尚需核实并实现接口 |
| `POST /auth/admin/pair-code` | 发放一次性配对码 | 用户选择、5 分钟倒计时、复制和重新发码；码仅短暂展示，不写日志 |
| `POST /auth/admin/devices` | 设备公开元数据 | 合并在线/离线、最近活动；仅有设备记录不等于在线 |
| `POST /auth/device/revoke` | 撤销设备 | 管理员验证、执行结果反馈、现有连接及时关闭 |
| `GET /workers` | 管理员 Worker 快照 | 用户归属、运行/空闲/失败状态；不是完整任务列表 |
| `GET /audit` | 当前内存审计事件 | 不能当作完整持久日志查询；增加有界分页和脱敏导出 |
| `GET /model-access` | 当前认证用户模型状态 | 不是全局模型管理接口；需单独实现管理员配置和用户绑定 |

当前配对码还绑定发码管理员的有效会话及目标用户状态。管理 App 若在发码后立即登出，会导致码失效；产品需要明确维护会话或调整为有审计的本地管理员授权机制，并覆盖过期、退出和停用测试。

### 6.2 中央管理权限与秘密保存

建议第一版本机管理走 Tauri 原生 IPC，由原生层访问受限的管理能力。工作设备连接使用 HTTPS/WSS。即使某个接口只监听 loopback，也不能因此取消管理鉴权；若采用管理 HTTP 通道，应使用独立授权和允许操作列表。

首次初始化只能作用于新的中央数据目录。已有账号库不能被安装器或初始化按钮覆盖。管理员身份与客户端配对用户分开，不要求普通使用者设置平台密码；如果保留管理员密码登录，密码只用于管理入口，不回流工作客户端。

模型账号在中央 App 中配置和查看状态。底层默认不要求 Keychain：Windows 使用当前用户 DPAPI 与严格 ACL；Mac 使用应用私有目录及受限文件权限。Mac 权限保护文件不是加密存储，不得写成“已加密”。上游登录由原生管理层/模型代理使用，渲染层只接收状态及脱敏标识；用户主动输入的密钥提交后清空，不回显保存值。

现有“只读使用外部模型登录”的语义继续保留：引用已有登录不等于允许刷新、退出或撤销它。新增由中央 App 自主管理的登录应使用独立配置，并明确更新所有权；模型接入实施前核实所用运行版本支持的实际登录方法。不要自动搬运其他程序的登录文件。

### 6.3 配置与进程管理

- 配置带版本，原子保存；校验失败不覆盖有效配置。磁盘、路径、权限和端口错误需可恢复。
- 服务启动前核验运行包、App Server 标识、数据目录和监听范围。不能只根据端口有响应就接管进程。
- 仅停止由本 App 创建并验证身份的进程；记录 PID、启动时间、程序路径，防止 PID 复用造成误杀。
- 操作状态包含未配置、已停止、启动中、运行中、停止中和失败；所有操作必须有超时和终态。
- 运行中改端口、目录或模型权限时说明影响。主动停止先停止接入新任务，并按已定义策略结束活动任务；未知结果不能自动重放。
- 第一版建议显式退出 App 时停止其受管中央服务；关闭窗口的行为在首次 UI 定稿时写清并测试。不隐式安装系统常驻服务。
- 网关、模型访问代理和 Worker 分别报告健康状态，不能用一个“在线”掩盖某一层失败。

### 6.4 HTTPS 与局域网配对体验

安装后需要能生成或配置服务器证书，明确“本机监听地址”和“给客户端使用的地址”。不得把 `localhost`、全部网卡监听地址或中央私有路径当作可用客户端连接地址。

第一版可保留管理员导出公共 CA 证书、客户端选择导入的明确流程；已有受信任证书则无需额外导入。配对码本身不证明服务器真实性，不能借简化配对关闭证书或主机名校验。地址变化、证书不匹配和证书过期应在 App 中可诊断。

## 7. Windows 中央运行是先决验证项

`services/test-gateway/src/worker-isolation.ts` 当前直接拒绝非 `darwin` 系统，并使用 `/usr/bin/sandbox-exec`。因此应先验证 Windows 运行与隔离，再投入完整管理页面开发。

需要逐项完成：

1. 在 Windows 原生构建带当前远端工作区补丁的 Codex App Server，核验 `yuan-zhou-remote-workspace/1`，保留固定版本和构建清单。
2. 抽象 Worker 启动接口，保留 Mac 现有隔离实现，增加 Windows 实现。具体受限令牌、ACL、进程和网络限制方案由原型实测确定。
3. 验证 Windows Worker 不能读取中央模型秘密、其他用户目录或执行客户端任务；只能访问自己运行所需资源及经授权模型代理。
4. 覆盖网络边界和子进程：Windows Job Object 负责进程回收，**本身不能证明文件、凭据或网络隔离**。
5. 处理 Windows 模型秘密文件所有者、ACL、reparse/链接和路径校验；不能沿用当前仅跳过 Unix mode 检查的分支宣布安全完成。
6. 运行真实模型和远端 Local Agent 闭环，含中断、重启、用户停用及设备撤销。若跨平台方案确需额外系统组件或管理员权限，先给出可运行原型和影响，再确认安装策略。

当前固定上游信息以 `harness/upstream.json` 为准：Codex `rust-v0.153.4`，commit `3d2ee51ca2d5db578f328aa75e20aa22c0197c9a`。本轮不顺手升级上游版本；需验证补丁的 Windows 构建，而不是改用另一个无补丁的可执行文件。

## 9. 验收矩阵与完成定义

### 9.1 两种中央系统都必须通过

| 场景 | 期望结果 |
|---|---|
| 干净环境安装 | 无本地开发工具、源码目录、全局 Node 或手动脚本也可配置并启动；运行时资源随包管理 |
| 配置持久化 | 中文/空格路径、重启恢复、端口占用、目录无权限、错误证书均有明确结果 |
| 服务生命周期 | 单实例与重复启动防护；正常退出、异常退出、启动失败后无受管进程泄漏，不影响其他服务 |
| 管理权限 | 创建/停用用户、配对码一次消费/过期、设备撤销；设备令牌无法调用管理接口 |
| 模型管理 | 可用、登录失效、限流、无绑定、权限停用分别显示；不把模型失败当作客户端离线 |
| 用户隔离 | 用户 A 不能使用用户 B 的会话/设备；Worker 不能读取中央上游登录或其他用户数据 |
| 真实执行位置 | 中央发出任务，目标客户端写入随机标记并回读；核对机器和工作区，结果来自客户端 |
| 中断与撤销 | 正在执行的客户端命令结束；授权终态不重连，普通网络故障可恢复；未知任务不自动重放 |
| 历史边界 | 同身份恢复；重新配对不偷偷转移旧 Thread 设备绑定；失败有可用的新建入口 |
| 打包维护 | 同版本覆盖、升级和回退保留已有数据；不支持的数据版本明确拒绝，回退前有可验证备份 |
| 日志导出 | 有界、脱敏；不含密码、令牌、模型登录文件、完整用户提示或工作区文件；导出内容可预览 |

至少验证 Windows 中央→Windows 客户端、Windows 中央→Mac 客户端、Mac 中央→Windows 客户端、Mac 中央→Mac 客户端四条真实链路。能在同一 Mac 上启动中央和测试客户端只是部分证据，不能替代跨机器 Windows 中央验收。
